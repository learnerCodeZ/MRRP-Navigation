# 为什么部署 HoloLens2 要从 Windows 切到 UWP

> 日期：2026-07-18
> 背景：Unity 里 Build Settings 切平台（Standalone Windows → Universal Windows Platform）是部署 HL2 的第一步。本文解释"为什么必须切"。

---

## 0. 一句话

HoloLens2 运行的是 **Windows Holographic 系统，只能装/跑 UWP 应用（AppX/MSIX 包）**。Unity 的 **Windows Standalone** 构建产出的是桌面 **`.exe`（Win32 程序）**，HL2 **装不上、也运行不了**。所以必须切到 **Universal Windows Platform (UWP)**，让 Unity 按 HL2 的应用模型去编译。

> 类比：就像给手机做 Android 包 vs 给电脑做 .exe——目标设备不同，产出的二进制格式、CPU 架构、权限模型、运行时全都不一样。HL2 本质上是个"UWP + ARM + 全息渲染"的设备，更接近一个应用商店 App，而不是桌面程序。

---

## 1. 根本原因：HL2 只认 UWP 应用

- HL2 的系统是 **Windows Holographic**（基于 Windows Core，但只能跑 UWP 沙箱应用）。
- 安装/侧载到 HL2 的都是 **UWP 打包的 AppX/MSIX 应用**（通过 VS 部署、Device Portal 装包、或商店）。
- Standalone Windows 构建产出 **Win32 `.exe`** —— 这是桌面程序格式，**HL2 没有桌面，运行时也不支持 Win32**，所以直接失败。

**结论**：要上 HL2，必须把构建目标设成 UWP，产出 HL2 能识别的 UWP 工程（`.sln`）→ 再打包成 AppX 部署。

---

## 2. Standalone vs UWP（HL2）对照

| 维度 | Windows Standalone | UWP（HL2 需要） |
|---|---|---|
| 产物 | `.exe`（Win32 桌面程序） | UWP 工程 → AppX/MSIX 包 |
| 系统能跑 | 普通 Windows 桌面 | HL2 Holographic / Win10/11 S 模式 / Xbox 等 UWP 宿主 |
| CPU 架构 | x86 / x64（桌面 Intel/AMD） | **ARM64**（HL2 是高通骁龙 ARM） |
| 运行时/后端 | 可用 Mono | **必须 IL2CPP**（HL2 不支持 Mono） |
| API 兼容 | .NET Framework / Full | **.NET Standard 2.1**（UWP 受限运行时） |
| 权限 | 桌面程序默认全权 | **沙箱 + Capabilities 声明**（联网/感知/摄像头要显式勾） |
| 全息/手势/空间 | 无（平面窗口） | **Holographic 立体渲染 + 手势 + 空间定位**（UWP App 模型才提供） |
| 部署 | 双击 .exe | VS 部署 / Device Portal 装包（USB PIN 配对） |

每一行的差异，都对应着 Build Settings 里要改的设置。

---

## 3. 这就解释了构建时为什么有那些硬性要求

| 构建设置 | 为什么（由 UWP/HL2 决定） |
|---|---|
| **平台 = UWP** | HL2 只跑 UWP 应用（见上） |
| **Architecture = ARM64** | HL2 CPU 是 ARM，不是桌面 x64 |
| **Scripting Backend = IL2CPP** | HL2/UWP 不支持 Mono；IL2CPP 把 C# 转 C++ 再编译，才能过 UWP 沙箱 |
| **API Compatibility = .NET Standard 2.1** | UWP 运行时受限，只认 .NET Standard 子集 |
| **Target SDK = 10.0.19041** | HL2 系统的 SDK 基线版本 |
| **Capabilities 勾选**（InternetClient / SpatialPerception 等） | UWP 沙箱靠能力声明给权限：**SpatialPerception** = 手势/空间网格，**InternetClient*** = 连机器人 ROS-TCP。**少勾一个，对应功能静默失效** |
| **Build Type = D3D** | 全息渲染用 DirectX（不是 OpenGL） |

> 记忆点：这些不是 Unity 随便设的门槛，而是 **HL2 这个设备（UWP + ARM + 全息）本身的硬约束**。Unity 只是照着目标设备的规矩编译。

---

## 4. 不用担心：切平台不会弄坏工程

- 切平台只是告诉 Unity **"当前为哪个目标编译"**，**不删除、不破坏**任何东西。
- **Editor 里的 Play Mode 测试照常能跑**（Standalone 模拟/MRTK 输入模拟），不受切平台影响。
- 随时可以**切回 Standalone**（Build Settings → Standalone → Switch Platform）继续用 .exe 测试，或再切 UWP 出设备包。
- 唯一成本：**首次切平台 Unity 要重新导入资源**（针对该平台处理纹理/着色器等），可能几分钟，正常。

> 日常开发用 Editor（快），出设备包时切 UWP——两边不冲突。

---

## 5. 流程位置

```
Editor 开发/测试(任意平台 Play Mode)
        │
        │  要部署到真机了
        ▼
Build Settings → 切 UWP → 配 ARM64/IL2CPP/Capabilities
        │
        ▼
Build → 生成 UWP .sln (C# 工程)
        │
        ▼
VS2022 打开 .sln → ARM64/Release → Deploy
        │
        ▼
HL2 上运行（手势画线 → /hrp_path → 小车）
```

"切 UWP"是这条链的**第一道门**——决定了后面产出的二进制 HL2 能不能认。

---

## 6. 复盘要点

- **HL2 ≠ 桌面 Windows**：它跑 Holographic 系统，只认 **UWP 应用**。Standalone 的 `.exe` 它装不了。
- **切 UWP = 按目标设备的应用模型编译**：UWP + ARM64 + IL2CPP + 能力声明 + 全息渲染，这些都是 HL2 的硬约束。
- **Capabilities 必勾**：SpatialPerception（手势/空间）、InternetClient*（联网到机器人）——UWP 沙箱的权限口子，少一个功能就废。
- **切平台安全**：不破坏工程，不影响 Editor 测试，随时可来回切；只是首次重新导入资源慢一点。
- **开发用 Editor，出机切 UWP**：两者并行不冲突。

---

**一句话**：HL2 只能跑 UWP 应用，Standalone 的 `.exe` 它不认；切 UWP 是为了让 Unity 按 HL2 的"应用模型 + ARM64 + IL2CPP + 能力声明 + 全息渲染"去编译，产出 HL2 能装能跑的包。这是部署的第一道门，且不影响日常 Editor 开发。
